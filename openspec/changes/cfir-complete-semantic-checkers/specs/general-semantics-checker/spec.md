## 新增需求

### 需求:节点有效性检查
系统必须在语义检查阶段验证节点有效性，对无效节点报告 `INVALID_NODE_AFTER_CHECK` 诊断。

#### 场景:语义检查后节点无效
- **当** CFIR 节点在 resolve 完成后仍处于错误状态
- **那么** 必须报告 `INVALID_NODE_AFTER_CHECK` 错误

### 需求:类型推断失败检查
系统必须在无法推断声明类型时报告 `UNABLE_TO_INFER_DECL` 诊断。

#### 场景:变量类型无法推断
- **当** 局部变量声明既无类型注解也无初始化表达式
- **那么** 必须报告 `UNABLE_TO_INFER_DECL` 错误

### 需求:多重赋值类型检查
系统必须检查多重赋值（解构赋值）的类型匹配性。

#### 场景:多重赋值类型不匹配
- **当** 多重赋值右侧表达式的类型与左侧模式不匹配
- **那么** 必须报告 `MISMATCHED_TYPES_MULTIPLE_ASSIGN` 错误，附带实际类型信息

### 需求:歧义使用检查
系统必须检测同名符号的歧义引用。

#### 场景:多个候选符号导致歧义
- **当** 一个名称引用在当前作用域中匹配到多个无法消歧的候选
- **那么** 必须报告 `AMBIGUOUS_USE` 错误，附带歧义名称

### 需求:子包冲突检查
系统必须检查顶层声明名与子包名的冲突。

#### 场景:声明与子包同名
- **当** 当前包中存在一个顶层声明，其名称与一个子包名相同
- **那么** 必须报告 `CONFLICT_WITH_SUB_PACKAGE` 错误

### 需求:可访问性检查
系统必须在成员访问点检查可见性约束。

#### 场景:访问不可见成员
- **当** 代码访问一个在当前上下文中因可见性限制而不可访问的成员
- **那么** 必须报告 `ACCESSIBILITY_ERROR` 错误，附带声明类型和可见性信息

#### 场景:主函数相关的可访问性提示
- **当** 可访问性错误涉及 main 入口函数相关的声明
- **那么** 必须报告 `ACCESSIBILITY_WITH_MAIN_HINT` 错误，附带额外的 main 提示信息

### 需求:参数个数通用检查
系统必须在通用上下文中检查参数个数匹配。

#### 场景:参数个数不匹配
- **当** 函数或构造器调用的参数个数与声明不匹配
- **那么** 必须报告 `PARAM_COUNT_MISMATCH` 错误，附带期望和实际个数

### 需求:core.Object 缺失检查
系统必须在 --no-prelude 模式下检查 core.Object 的存在性。

#### 场景:no-prelude 模式下找不到 Object
- **当** 编译选项启用了 --no-prelude 且 std/core 中找不到 Object 类
- **那么** 必须报告 `CORE_OBJECT_NOT_FOUND_WHEN_NO_PRELUDE` 错误
