## 上下文

`PsiRawCfirBuilder` 的 golden 测试目前主要集中在 `rawBuilder/declarations` 和少量 `expressions/*` 子目录，存在以下问题：
- 同一语法域分散在多个目录，命名语义不稳定，难以按语法特性检索。
- 现有用例偏重“是否能转换”，缺少“语法边界/错误恢复/仓颉特性”系统覆盖。
- 新增 PSI 节点或转换分支后，没有强约束确保新增测试资产，导致回归风险向后累积。

本次变更保持现有测试框架（golden 文件 + 生成测试类）不变，通过重组 testData 与增加覆盖矩阵来提高可维护性与可审计性。

## 目标 / 非目标

**目标：**
- 建立稳定、可扩展的 `rawBuilder` 测试目录规划，按语法域组织而非按历史文件散列。
- 覆盖仓颉语法到 Raw CFIR 的核心转换路径、语法边界和错误恢复路径。
- 定义覆盖矩阵与门禁规则，确保新增语法节点时测试资产同步更新。
- 保持现有执行入口（`generateRawCfirBuilderTests` + `:psi2cfir:test`）可持续使用。

**非目标：**
- 不在本变更中修改 `PsiRawCfirBuilder` 生产逻辑。
- 不引入新的测试运行器或替换 golden 对比机制。
- 不一次性重构 `raw-cfir` 之外模块的测试组织。

## 决策

1. 目录采用“语法域 + 主题”二级结构，而不是继续平铺文件。
- 选项 A：继续平铺并仅改命名。缺点是规模增长后无法表达覆盖边界。
- 选项 B：按语法域分组（采用）。优点是可直接映射语法规范章节并支持 coverage matrix。

2. 用“单特性最小用例 + 组合场景补充”替代“大而全示例”。
- 选项 A：每个文件覆盖多个语法点。缺点是失败定位困难、golden diff 噪音大。
- 选项 B：以最小用例为主（采用），再补充少量组合场景验证交互行为。

3. 保留 `.cj + .txt + .lazyBodies.txt` 三件套，按需允许无 `.lazyBodies.txt`。
- 选项 A：统一强制三件套。缺点是维护成本高，部分场景无额外价值。
- 选项 B：保留当前机制并按需要生成（采用），避免无意义冗余。

4. 覆盖矩阵以“语法节点 -> 用例文件”映射落地在 testData 辅助清单中，并在测试阶段校验。
- 选项 A：仅文档约定。缺点是缺乏自动约束，易退化。
- 选项 B：增加可校验矩阵（采用），在 CI 中暴露缺口。

## 风险 / 权衡

- [迁移期间大量 golden 变更] → 分批迁移目录，保证每批可独立通过 `:psi2cfir:test`。
- [目录重命名导致历史定位困难] → 提供迁移映射表（旧路径 -> 新路径）并在变更说明中固化。
- [覆盖矩阵维护成本增加] → 将矩阵粒度限制为“语法节点级”而非“每个 token 级”，并在新增语法流程中模板化更新步骤。
- [表达式组合爆炸] → 采用“核心组合优先”，对低价值笛卡尔组合不做穷举。

## 迁移计划

1. 建立新目录骨架与命名规则，先不删除旧数据。
2. 按语法域迁移现有样例并保持测试绿灯。
3. 补齐缺失语法样例，更新 golden。
4. 引入覆盖矩阵与校验，修复新增失败项。
5. 删除已迁移的旧路径与冗余样例，更新生成测试索引。
6. 在 CI 中跑 `:cfir:raw-cfir:psi2cfir:test` 作为收口验证。

回滚策略：若迁移批次引入大面积回归，保留旧目录并回退当批目录变更，确保主干测试可恢复。

## 开放问题

- 覆盖矩阵放在 `testData/rawBuilder` 下还是测试源码目录下，哪种更符合当前工具链读取习惯？
- 对“尚未实现但语法已解析”的节点，是否先以错误恢复黄金文件占位，还是延期到语义实现后再补？
- 是否需要为仓颉特性（`extend`、`match`、`spawn`、`VArray`）单独定义最低覆盖门槛（例如每项至少 N 个场景）？
