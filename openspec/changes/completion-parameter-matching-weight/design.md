# 设计：实参位的期望参数类型与补全权重

## 上下文

- **权重位段现状**（10.3 已落地部分）：来源 / import 成本 / 期望类型匹配 / 类别 / 弃用 / 同级声明次序各占一个互不重叠的位段，步长**严格大于其下各维全幅跨度**，并有极值验算用例（`Int.MAX_VALUE`/`MIN_VALUE`）。
- **期望类型的实现面**：契约 `analysis/analysis-api/.../components/CaExpressionTypeProvider.kt`；实现只有 `analysis-api-cfir` 一处。
- **2026-10-11 复核证据**：该实现中没有任何从「所在调用表达式的实参位」推导期望参数类型的代码（`CjValueArgument` / `argumentIndex` / `valueArguments` 与 expected 相关的 grep 无命中）。
- **补全侧消费点**：`code-insight/completion/impl-cfir/filter/CfirExpectedTypeCompletionFilter.kt` 读 `position.expectedType`；排序数据在契约的 `CompletionSortDataImpl`。

## 目标 / 非目标

**目标：**

- 位置落在实参内时，期望类型＝该位形参的类型（命名实参照形参名匹配）；
- 该结论沿既有「期望类型匹配」一维进入排序：匹配加权、未知不加权、不匹配不惩罚；
- IDE 与 LSP 两端候选与排序一致（共用同一份结论）。

**非目标：**

- 不新增权重维度、不注册平台 weigher（10.3 已定的做法：`priorityOf` 一次性折算）；
- 不实现 A4 的 extension 适用性检查（另一件事）；
- 不做「实参个数/顺序的合法性」判断（那是诊断的活，不是补全排序）。

## 决策

- **D1：推导放分析层。** 放补全侧会让 LSP 与 IDE 各写一份、必然漂移；`expectedType` 是两端的公共契约，实参位分支补在这里最省。若推导需要新的公开语义（例如「该位形参名」），先在 `analysis-api` 的契约文档里写清，再在 cfir 实现。
- **D2：未知必须静默。** 推导不出（被调方未解析、实参位超出形参表、变长/重载歧义）→ 返回「未知」；补全侧对未知不产生任何影响。**禁止**用形状猜测（例如「名字像类型就加权」）。
- **D3：复用既有位段与步长约束。** 参数匹配是「期望类型匹配」的一种上下文，不是新维度；位段布局与步长约束不变，极值用例继续有效。

## 风险 / 权衡

- **静默错排**：推导错误只表现为「顺序没道理」，不报错——用正反例（匹配/不匹配/未知）与极值用例钉死。
- **性能**：每次补全多一次符号解析；进 13.2 的具名预算文件（`CONTEXT`/`INDEX_QUERY` 档）观察，超预算按 §13.2 的门禁处理。
- **重载歧义**：同名重载的形参表不同时，若无法唯一确定被调方，按 D2 返回未知（宁少不错）。
