## 新增需求

### 需求:L1 LSP 与原生补全共用同一候选生成实现
LSP 必须与 IDE 原生补全共用同一份候选生成、可见性、过滤与排序实现。`:lsp` 只承担协议适配与扩展点装配，禁止在 `:lsp` 重新实现候选生成、作用域计算、适用性判定或排序。接入方式按 §7.11.0 前置实验的结果二选一：走平台补全进程（注册上游描述符声明的 `completion.contributor`），或在该扩展点不可用时直接驱动上游 section 管线；**两者都必须经过同一份占位标识符修正**（否则在裸占位上分析会得到空候选且不报错）。

#### 场景:两端同源
- **当** 同一份仓颉源码在 IDE 与 LSP 中请求同一位置的补全
- **那么** 两端呈现的候选符号集合必须来自同一次管线；LSP 不得维护独立的候选来源或降级算法

#### 场景:不得复制语义
- **当** 实现 LSP 侧转换
- **那么** `:lsp` 不得访问 CFIR resolver 状态、不得自行判断可见性或适用性、不得按显示名去重；这些职责一律留在上游

### 需求:L2 无头容器的扩展点装配
LSP 运行环境不加载插件描述符，`com.intellij.completion.contributor` 等平台扩展点在其中不存在。`:lsp` 必须显式 prime 这些扩展点，再由上游描述符装载实现声明。禁止手工注册替身贡献者来掩盖装配缺失。

#### 场景:上游描述符装载
- **当** LSP 启动并注册服务
- **那么** 仓颉补全 contributor 必须由上游单职责描述符装载，且在测试中验证其确实被调用；不得在测试或运行期手工 new 一个 contributor 塞进扩展点

#### 场景:扩展点缺失时的退化
- **当** 目标平台上 `completion.contributor` 无法被 prime
- **那么** 必须退化为直接调用 `CompletionService` 的 provider 入口，并把实测结论写入实施记录；不得静默返回空结果或抛未捕获异常

### 需求:L3 补全项字段映射
必须把平台补全结果映射为 LSP `CompletionItem`，至少包含标签、排序文本、详情、描述、类型、编辑与会话数据。映射规则必须与 IDE 侧呈现一致。

#### 场景:字段来源
- **当** 一个候选被转换为 `CompletionItem`
- **那么** `label` 取呈现文本或查找串，`labelDetails.detail` 取尾文本，`labelDetails.description` 取类型文本，`kind` 按符号/PSI 类型映射，不得一律降级为 `Text`

#### 场景:未设置的字段
- **当** 构造 `CompletionItem`
- **那么** 不得擅自设置 `commitCharacters`、`filterText`、`preselect`、`deprecated`、`tags`；排序与前缀过滤由服务端预排序与客户端默认行为承担

### 需求:L4 排序与服务端一致
列表顺序必须由服务端既有排序决定，并通过 `sortText` 表达，使客户端的字符串比较结果与服务端顺序一致。禁止在 LSP 侧另建一套与上游排序无关的排序规则。

#### 场景:排序文本
- **当** 服务端已按上游权重排好候选
- **那么** `sortText` 必须编码该顺序；禁止按标签重新排序或交给客户端自由排序

### 需求:L5 应用、resolve 与会话生命周期
必须在协议命令中完成候选应用，并支持 `completionItem/resolve` 补齐文档。保留活对象的实现必须为会话设定有效期；会话失效时返回明确错误，禁止崩溃或写入过期内容。

#### 场景:应用候选
- **当** 客户端接受某个补全项
- **那么** 真实文本变更（含必要的 import 编辑与光标移动）必须以协议允许的方式回传，且与 IDE 侧插入结果一致

#### 场景:补全项 resolve
- **当** 客户端对某个补全项发起 resolve
- **那么** 必须返回该候选的文档内容；无法恢复语义时返回可诊断的失败，不得伪造文档

#### 场景:会话过期
- **当** 客户端持有的会话键已过期
- **那么** 服务端返回明确的会话过期错误，提示重新请求补全；禁止抛出未捕获异常或返回错误位置的编辑

### 需求:L6 替换既有退化实现并给出对比证据
必须整体替换既有的「解析变体优先、回退到工作区全量声明遍历」实现。**默认路径只保留新实现**；旧实现仅在独立开关下临时保留，且不得成为与新实现并行的第二条默认候选路径，并在验收通过后由后续变更删除。替换前后必须有同场景对比用例。

#### 场景:同场景对比
- **当** 在同一批源码位置上比较替换前后
- **那么** 新实现给出的可见符号集合必须严格不少于旧实现；旧实现的全工作区遍历路径不得出现在**默认路径**中

#### 场景:不再按击键扫描全工作区
- **当** 一次补全请求在没有候选时
- **那么** 不得退化为遍历全部工作区文件的所有命名声明

### 需求:L7 线程与生命周期差异
LSP 运行在 headless 容器上，其线程模型与生命周期失效语义与 IDE 不同，必须单独验证，不得假设与 IDE 一致。

#### 场景:请求线程内完成
- **当** 在 LSP 请求线程中执行补全
- **那么** 分析、快照构造与结果转换必须在该线程内完成，不得跨线程共享未受保护的会话状态

#### 场景:失效语义
- **当** headless 容器中的分析会话令牌失效
- **那么** 必须走与 IDE 一致的可诊断失效路径（重新请求），不得触发断言失败或返回陈旧结果

### 需求:L8 降级与可观测性
必须定义无候选、取消、分析失败与受限分析时的行为，并记录阶段耗时、候选量与失败类别。禁止把异常吞成空列表。

#### 场景:无可用候选
- **当** 当前位置没有任何合法候选
- **那么** 返回合法的空列表而非异常；`isIncomplete` 的取值必须与实际是否已穷尽候选一致

#### 场景:请求取消
- **当** 客户端在补全计算期间取消请求
- **那么** 计算必须及时停止并释放资源，且不得留下跨请求的状态

#### 场景:统计与隐私
- **当** 记录补全耗时与候选量
- **那么** 不得记录完整源码或文档内容

### 需求:L9 插件侧 LSP 客户端注册补全能力
IDE 内置的 LSP 客户端必须注册补全能力，使 LSP 服务端提供的补全可在该宿主内被使用。

#### 场景:能力声明与实现一致
- **当** 宿主声明了补全相关能力
- **那么** 必须实际注册对应能力实现；不得只声明能力而没有任何已注册的处理组件
