## 上下文

本变更面向 `cfir/analysis-tests/testData/diagnostics2`，目标不是实现新的 Kotlin 诊断逻辑，也不是接入现有测试体系，而是先为后续实现建立一套按语义域组织的测试数据矩阵。

本变更有一个硬性前置条件：在写任何 `.cj` 测试数据之前，必须先完整阅读并尽可能读透相关仓颉语言语义。这里的“读懂”不是仅浏览目录或依赖项目当前实现，而是要先通过仓颉文档 MCP 获取官方语义描述，再进入官方 C++ 编译器实现核对真实行为与边界，最后才参考本项目当前 `CfirErrors`、checker 和已有测试数据。任何没有读透的语义都不能靠猜测落成测试样例。

这里的“读透”必须收敛成可执行标准，而不是主观感觉。对每一个准备写测试数据的语义域，作者都必须先回答清楚四类问题：
1. 该语义域的核心语言规则是什么。
2. 哪些形式是合法的，哪些形式是非法的。
3. 错误的边界条件和例外条件是什么。
4. 文档与官方 C++ 实现之间是否存在仍未解释清楚的差异。

只有当这四类问题都能用仓颉文档 MCP 和官方 C++ 编译器实现中的证据支撑时，才算“已经读懂”，才允许开始编写该语义域的 `.cj` 测试数据。

当前仓库已经具备三类直接证据：

1. **项目内诊断定义总表**：`cfir/checkers/checkers-component-generator/src/org/cangnova/cangjie/cfir/checkers/generator/diagnostics/CfirDiagnosticsList.kt`
   - 已经将 CFIR 语义诊断分为 Resolve、Redeclaration、Imports、SuperTypes、Extend、DeclarationStatus、CallResolution、Initialization、GenericAccess、Mutability、Annotation、Interop、Effects、Match、Constraint、TypeCheck、ConstEval、Unresolved 等语义组。
2. **现有覆盖缺口盘点**：`cfir/analysis-tests/diagnostics-coverage-gap-vs-cpp.md`
   - 明确指出当前 suite 的主要问题已经不是“完全没测”，而是覆盖不均、目录偏薄、名称级回归缺失，以及某些 checker 根本没有接入默认注册链路。
3. **官方语义基线**：`external/cangjie_compiler/src/Sema/Diags.h` 与 `TypeCheck*`、`PatternUsefulness.cpp`、`LegalityOfUsage/*`
   - 官方 C++ `SEMA` 侧已经稳定体现 imports / calls / inference / match / this-super legality / extend / inheritance / mutability / visibility / initialization / range / throw-catch / interop / effects 等语义域。

此外，仓颉文档 MCP 是本变更的语义第一入口：在编写每一类测试数据前，应先从文档中确认语言规则、术语和限制；若文档表述不充分或与实现存在张力，再继续深入官方 C++ 编译器实现，直到把语义边界读懂为止。

因此，本变更不接受“边写边理解”的工作方式。允许测试数据先于实现，但不允许测试数据先于语义理解。每一批测试数据都应当建立在先完成该语义域阅读、再形成证据清单、最后才落样例的顺序上。

测试数据表达约束已经明确：

- 已定义诊断仍使用内联标记 `<!DIAGNOSTIC!>...<!>` 表达。
- 未定义诊断也必须使用内联标记 `<!DIAGNOSTIC!>...<!>` 表达，并且建议诊断消息与来源说明必须紧贴在同一段内联诊断范围内，例如 `<!DIAGNOSTIC!>/* suggested message */code<!>`；不要求为了这些消息去修改 Kotlin 代码或接入消息体系。

## 目标 / 非目标

**目标：**

- 为 `cfir/analysis-tests/testData/diagnostics2` 建立一套按仓颉真实语义域组织的测试数据覆盖方案，而不是继续按零散缺口追加个例。
- 统一定义测试数据来源优先级：优先使用仓颉文档 MCP 与官方 C++ 编译器语义，再对照项目当前 `CfirErrors` 与现有 checker/resolve 行为。
- 明确区分三类测试数据：
  1. **已定义诊断、可直接使用内联标记补样例**
  2. **官方语义明确、但项目尚未定义诊断名，仍必须使用内联标记，并在同一段内联范围内补建议消息与来源说明**
  3. **语义方向存在，但当前项目实现未必可触发，测试数据仍可先作为语义样例沉淀，不要求接入或验证执行**
- 为后续实现者提供一份能够直接据此批量编写 `.cj` 文件的目录与分批推进策略。

**非目标：**

- 不修改 Kotlin 生产代码，不新增 diagnostic factory、default message、renderer 或 checker 注册。
- 不要求将 `diagnostics2` 接入现有生成器、generated suite、all-files-present 或任何现有测试运行链路。
- 不要求执行编译、测试或其他验证命令来证明这些测试数据当前可运行。
- 不承诺本次提案会让所有官方语义立即在当前编译器实现下可触发；对当前未实现的语义，允许先以内联诊断 + 内联范围内消息说明方式表达。
- 不允许在尚未完整读懂语义的情况下凭猜测补写测试数据。
- 不把 parser / lexer / macro runtime 层面的错误混入这次 CFIR 语义测试矩阵。

## 决策

### 决策 1：以“语义域矩阵”而不是“诊断名清单”组织测试数据

选择按语义域组织目录与任务，而不是单纯枚举 `CfirErrors` 中尚未覆盖的诊断名。

原因：
- `CfirErrors` 适合做名称级核对，但无法单独表达仓颉真实语义边界。
- 官方 C++ `SEMA` 代码天然按语义域实现；后续实现者也更容易按 `calls / match / extend / initialization / range / throw / effects` 等域逐批推进。
- 同一个语义域中可能同时包含：已实现诊断、官方稳定语义但尚未命名的诊断、以及暂不可达的 blocked 分支。按语义域组织更利于真实落地。

备选方案：按 `CfirErrors` 分组逐个补齐。

不采用原因：这种方式容易得到“名称覆盖看起来完整，但真实语义矩阵仍然破碎”的假完整状态。

### 决策 2：对未定义诊断采用“内联诊断 + 内联范围内建议消息”作为过渡机制

对于项目当前尚未定义但官方语义明确的场景，测试 `.cj` 文件仍然使用内联诊断，并在同一段内联范围内通过紧贴错误代码的注释说明：
- 建议的诊断消息
- 对应的官方语义来源
- 必要时补充当前尚未进入项目正式诊断定义的状态说明

原因：
- 用户明确要求测试样例要先于实现落地，且不要为了测试而越界改 Kotlin 代码。
- 这样既能保持整个矩阵的断言形式统一，又能把“语义事实”沉淀到 testData 中，后续实现者据此补 producer/checker，不会丢失语义上下文。

备选方案：只写当前项目已有诊断。

不采用原因：这会把大量官方稳定语义排除在外，无法满足“最后能基于整个仓颉测试样例去实现真实功能”的目标。

### 决策 3：允许“测试数据先行”，不要求当前可触发

对于仓库内当前未必已经接通或完全可触发的诊断场景，规范不要求先补测试基础设施或生产代码；只要求先把语义样例写进 `diagnostics2`。

原因：
- 用户明确要求当前阶段只编写测试数据，不越界处理现有测试体系和执行链路。
- 先沉淀测试数据比先改接线更符合本变更目标。

备选方案：先接通 `diagnostics2` 再写测试数据。

不采用原因：这超出了当前用户要求的“只改提案，只写测试数据”边界。

### 决策 4：分三层来源对齐语义事实

测试数据语义依据按以下优先级决定：

1. 仓颉文档 MCP
2. 官方 C++ 编译器 `SEMA` 实现与现有单测/引用路径
3. 本项目当前 `CfirErrors`、checker、resolver 行为

原因：
- 用户明确要求“不要自己猜测”。
- 项目当前 `CfirErrors` 并不完整，不能把项目实现现状当成语义上限。
- 只有先读懂文档和官方实现，写出来的测试数据才可能是真实仓颉语义，而不是项目当前缺口的镜像。

备选方案：只对齐项目当前实现。

不采用原因：这只会复制当前缺口，而不是建立真实仓颉语义基线。

### 决策 5：把“已读懂语义”定义为有证据清单支撑

本提案不把“我大概知道这个语义”视为已理解。对于每个语义域，必须先形成最小证据清单，至少包括：
- 文档 MCP 中的对应章节或条目
- 官方 C++ 编译器中的对应 `Sema/*` 或诊断定义位置
- 该语义域的合法/非法/边界条件摘要
- 若存在分歧，明确列出未确认点

原因：
- 这样可以把“读懂”从主观判断收敛成可检查的前置条件。
- 这样写出来的测试数据才能真正对应仓颉语言语义，而不是作者的记忆或推断。

备选方案：把“读懂”保持为宽泛要求，由执行者自行判断。

不采用原因：这会导致不同语义域的理解深度不一致，重新引入凭印象补样例的问题。

## 风险 / 权衡

- **官方语义与当前项目实现不一致** → 在 spec 和任务中明确把“已实现可断言”与“官方语义先行、需内联并附带建议消息说明”分层，不把两者混成同一批完成标准。
- **语义理解不充分导致样例失真** → 把“先完整阅读仓颉文档 MCP 与官方 C++ 实现”写成前置条件；没有读懂就不允许落测试数据。
- **把‘读过’误当成‘读透’** → 在任务中增加语义域证据清单要求；没有证据清单就不允许进入该域的测试数据编写。
- **新增 `.cj` 文件过多导致目录失控** → 先定义 `diagnostics2` 下的语义域目录和命名规则，再按批次补文件，避免随意铺散。
- **未定义诊断注释风格不一致** → 在 spec 中统一约定“内联诊断 + 内联范围内说明”模板，确保每个未定义诊断至少包含内联诊断名、建议消息、来源三项。
- **blocked 场景与普通缺口混淆** → 在任务分组中单列“blocked / 前置实现依赖”批次，避免执行阶段误判。

## 迁移 / 推进计划

本变更不涉及运行时代码迁移；推进计划体现在测试数据落地顺序：

1. 先补当前 `CfirErrors` 已定义且适合直接表达的名称级缺口。
2. 再补官方 C++ 已稳定存在、但本项目尚未形成名称级保护的薄弱语义域。
3. 对项目尚未定义的诊断，在对应位置使用内联诊断，并在同一段内联范围内表达建议诊断消息与来源说明。

在上述推进顺序之前，还有一个总前置步骤：先按语义域完成相关仓颉语义的阅读、核对和证据清单整理，再开始写测试数据。

## 开放问题

- 仓颉文档对 `range`、`throw/catch`、`effects`、`inout` 等语义边界的公开描述是否与官方 C++ 当前实现完全一致；若不一致，应以哪个版本行为作为测试样例主基线。
- 对“未定义诊断的内联范围内建议消息”是否要统一写成固定中文/英文消息模板，还是允许按语义场景自由描述。
- 一些官方稳定语义（如更完整 interop、mock、common/specific）当前是否应全部进入本变更首批 spec，还是先作为 backlog capability 下的后置目录。
