## 新增需求

### 需求:按仓颉语义域组织 CFIR 诊断测试数据
系统必须为 `cfir/analysis-tests/testData/diagnostics2` 建立一套按仓颉真实语义域组织的测试数据覆盖方案，而不是只按零散诊断名被动补样例。

#### 场景:编写前必须先读懂仓颉语义
- **当** 准备为 `diagnostics2` 编写任何新的语义诊断测试数据
- **那么** 必须先通过仓颉文档 MCP 阅读相关语言规则，并进一步结合官方 C++ 编译器实现确认真实语义边界，之后才允许开始编写测试数据

#### 场景:语义仍不清楚时不得写样例
- **当** 仓颉文档 MCP 与官方 C++ 编译器实现仍不足以支撑某个语义场景的真实判断
- **那么** 当前阶段不得凭猜测写出对应测试数据，而必须先将该语义场景标记为未确认

#### 场景:按语义域形成最小证据清单后才可写样例
- **当** 准备为某个具体语义域补写 `diagnostics2` 测试数据
- **那么** 必须先形成该语义域的最小证据清单，至少包括文档 MCP 条目、官方 C++ 编译器对应位置、合法/非法/边界条件摘要，以及仍未确认的歧义点

#### 场景:没有证据清单不视为已读懂
- **当** 某个语义域尚未形成最小证据清单
- **那么** 不得将该语义域视为“已经读懂”，也不得开始编写其测试数据

#### 场景:以官方 SEMA 语义域划分测试目录
- **当** 为 CFIR 语义分析补充新的诊断测试数据
- **那么** 测试目录必须优先按 imports、calls、inference、match、references、extend、inheritance、visibility、mutability、initialization、effects、range、throw、try、interop 等语义域归类

#### 场景:项目已有诊断与官方语义同时参与建模
- **当** 一个语义场景在项目 `CfirErrors` 中已有诊断名，或在官方 C++ `SEMA` 中已有稳定语义依据
- **那么** 该场景必须被纳入语义域矩阵规划，而不能因为当前目录中没有现成位置就被忽略

### 需求:使用内联诊断标记表达已定义诊断
对于项目当前已经定义的诊断，测试数据必须使用内联标记形式 `<!DIAGNOSTIC_NAME!>...<!>` 表达预期错误位置。

#### 场景:为已有诊断编写 `.cj` 用例
- **当** 测试场景对应 `CfirDiagnosticsList.kt` 中已经存在的诊断工厂
- **那么** `.cj` 文件必须使用框架支持的内联诊断标记形式断言诊断名称与范围

#### 场景:诊断名带有 CFIR 前缀
- **当** 诊断来源在运行时带有 `CFIR_` 前缀
- **那么** 测试样例仍必须使用框架规范化后的诊断名书写，而不要求手写前缀

### 需求:对未定义但语义明确的诊断使用内联标记并补充内联范围内说明
对于官方仓颉语义明确存在、但本项目当前尚未在 Kotlin 代码中定义 diagnostic factory 的场景，测试数据仍必须使用内联诊断标记表达预期错误位置，并在同一段内联诊断范围内补充建议诊断消息与语义依据说明。

#### 场景:官方 C++ 已有稳定语义但项目尚未定义诊断
- **当** 某个 `.cj` 用例表达的语义错误在官方 C++ `SEMA` 中稳定存在，但本项目当前没有同名诊断
- **那么** 该用例必须在相应错误片段上使用内联诊断标记，并在同一段内联范围内注明建议诊断消息和来源依据

#### 场景:内联范围内说明的最小信息集
- **当** 为未定义诊断编写内联范围内说明
- **那么** 说明中必须至少包含“建议诊断消息”“官方文档或官方 C++ 依据”两项信息；诊断名由对应内联诊断标记承担

### 需求:允许测试数据先于测试体系接线存在
测试数据规划允许 `diagnostics2` 目录中的样例先作为语义样例存在，而不要求当前阶段接入现有生成器、all-files-present 或测试执行链路。

#### 场景:新目录尚未接入现有测试体系
- **当** 在 `cfir/analysis-tests/testData/diagnostics2` 下新增测试数据
- **那么** 当前阶段不要求同步修改生成器或测试运行链路来让这些文件立即被执行

#### 场景:当前实现尚未支持该语义
- **当** 某个语义错误在官方语义中成立，但当前项目实现尚未定义或尚未可触发
- **那么** 仍然允许先编写 `.cj` 测试样例，在对应位置使用内联诊断标记，并在同一段内联范围内补充建议诊断消息与来源说明

### 需求:覆盖策略必须同时维护名称级回归和语义域回归
测试数据补全必须同时维护“哪些诊断名尚未被直接 inline 断言”与“哪些官方语义域尚未形成目录与矩阵”两条清单，避免只做其一。

#### 场景:已有语义目录但缺名称级保护
- **当** 某一语义目录已经存在 smoke coverage，但仍有已定义诊断未被直接 inline 断言
- **那么** 后续补全必须把该诊断加入名称级覆盖清单，而不是仅以已有目录存在为完成标准

#### 场景:已有诊断名但缺整块语义域
- **当** 官方 C++ `SEMA` 中存在稳定语义域，但当前 `testData/diagnostics2` 尚未形成对应目录或矩阵
- **那么** 后续补全必须优先为该语义域建立目录、命名策略和核心样例，而不是只在其他目录中零散追加个例

### 需求:新增测试文件只要求落在 diagnostics2 目录
任何新增的 `.cj` 测试文件都必须放置在 `cfir/analysis-tests/testData/diagnostics2` 下，但当前阶段不要求它们被现有测试体系递归发现或执行。

#### 场景:新增目录或 `.cj` 文件
- **当** 在 `cfir/analysis-tests/testData/diagnostics2` 下新增目录或测试文件
- **那么** 其位置和命名必须服务于语义组织与后续实现理解，而不是为了当前测试接线

#### 场景:目录仅用于占位规划
- **当** 某个语义域尚未准备好进入当前批次实现
- **那么** 提案可以先在设计和任务中定义其目录与命名策略，但不得通过新增无法维护的空目录或无意义占位文件制造虚假覆盖
