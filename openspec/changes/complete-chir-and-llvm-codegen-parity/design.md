## 上下文

当前仓库已经具备 Kotlin/JVM 编译器主干与部分后端尝试，但 CHIR 与 `CHIR -> LLVM IR` 链路未形成可闭环、可验证的一致实现，现有结果与 `external/cangjie_compiler` 的 LLVM IR 存在行为差异。  
本变更覆盖多个模块（CHIR 模型、lowering、LLVM 互操作、CLI 产物输出、测试基线），并引入本地 LLVM API 访问策略（JNI/JNA），属于跨域架构变更。  
约束条件：
- 不关心 CHIR 上游来源，只要求 CHIR 消费端与代码生成端完整正确。
- 最终 LLVM IR 必须与参考编译器产物完全一致（语义与文本稳定输出层面）。
- 项目为 Kotlin/JVM（JDK 17），需在 JVM 环境中稳定调用 LLVM 能力。

利益相关者：
- 编译器后端开发者：需要可维护、可扩展的 CHIR 与 lowering 架构。
- 测试与发布维护者：需要可回归、可比对的一致性验证机制。
- CLI 用户：需要获得稳定、正确的 LLVM IR 产物。

## 目标 / 非目标

**目标：**
- 建立完整 CHIR 语义与校验链路，形成后端可依赖的接口优先（interface-first）抽象。
- 实现覆盖核心语言特性的 `CHIR -> LLVM IR` lowering 与代码生成，消除当前不正确实现。
- 引入稳定的 LLVM API 互操作层（JNI/JNA），并将平台差异隔离在基础设施边界内。
- 建立参考编译器对齐验证：给定同一输入，Kotlin 编译器输出的 LLVM IR 与参考产物一致。
- 形成分层测试（单元、模块、端到端 golden）与回归门禁。

**非目标：**
- 不改造 CHIR 的上游生成器实现或其前端策略。
- 不在本次变更中引入新的语言特性语义，仅对齐既有语义。
- 不以“最小可跑通”为目标；本变更要求全量正确性与一致性。

## 决策

### 决策 1：CHIR 语义层采用“核心 IR + 校验器 + 访问接口”分层
- 方案：在现有 CHIR 模块上补齐统一数据模型、类型/控制流语义约束与校验通道，公开只读接口，隐藏实现细节。
- 原因：避免后端直接依赖可变实现细节，满足模块边界与可替换实现要求。
- 备选方案：
  - 直接在 lowering 阶段容错并修补 CHIR：会放大隐式行为，难以定位错误，放弃。
  - 将校验逻辑分散到各 lowering pass：重复高且一致性差，放弃。

### 决策 2：代码生成采用“可组合 lowering pass + 明确阶段边界”
- 方案：按符号收集、类型映射、控制流转换、运行时接入、IR 规范化等阶段拆分 pass，并定义阶段输入/输出契约。
- 原因：降低复杂度，便于差异定位与回归测试；与 K2 风格流水线保持一致。
- 备选方案：
  - 单体式一次性生成 LLVM IR：实现快但不可维护，不利于 parity 调试，放弃。

### 决策 3：LLVM 互操作层抽象为 Backend API，底层支持 JNI/JNA 实现
- 方案：定义 Kotlin 侧 `LlvmBackendApi` 接口，提供至少一个生产实现；实现内部可按平台选择 JNI 或 JNA。
- 原因：避免业务层绑定具体桥接方案，便于后续性能优化与平台适配。
- 备选方案：
  - 直接在代码生成层散布 JNA 调用：耦合严重、难测试，放弃。
  - 仅 JNI：性能可控但开发与维护成本高；保留为可选实现，不强制唯一方案。
  - 仅 JNA：开发快但性能和类型安全可能不足；同样保留为可选实现，不强制唯一方案。

### 决策 4：一致性判定采用“双层对齐”
- 方案：
  - 语义层：以模块、函数、全局对象等结构化要素对齐。
  - 文本层：对 IR 输出做稳定化后进行文本逐项对比，目标为“完全一致”。
- 原因：仅文本比对易受命名与顺序噪音影响；仅语义比对不足以保证交付要求。
- 备选方案：
  - 只做文本比对：误报率高，定位困难，放弃。
  - 只做语义比对：无法满足“产物完全一致”要求，放弃。

### 决策 5：基于参考实现构建 golden 回归体系
- 方案：使用 `external/cangjie_compiler` 生成基线 IR，建立样例集与回归测试，CI 中对关键样例强制校验。
- 原因：让“与参考产物一致”从口头要求变为自动化门禁。
- 备选方案：
  - 手工抽样对比：不可持续且易回退，放弃。

## 风险 / 权衡

- [风险] JNI/JNA 与 LLVM 版本/ABI 不匹配导致运行时崩溃  
  → 缓解：锁定支持矩阵；在加载阶段执行版本探测与失败降级；增加启动自检。

- [风险] 为达成文本一致性引入大量稳定化逻辑，影响可读性与性能  
  → 缓解：稳定化规则集中管理并可开关；默认面向测试与发布配置启用。

- [风险] 大规模替换现有后端路径造成回归面扩大  
  → 缓解：按阶段迁移，保留对照输出模式；引入分层测试和里程碑门禁。

- [权衡] 先对齐参考实现可能限制短期内架构自由度  
  → 缓解：通过接口抽象隔离“对齐策略”与“实现机制”，后续可平滑演进。

## 迁移计划

1. 建立 CHIR 语义校验层并接入现有流水线，先保证输入一致性。
2. 引入新的 lowering pass 框架并实现核心特性，对齐小规模样例。
3. 接入 LLVM Backend API（JNI/JNA），替换旧的实验路径。
4. 建立 golden 基线与差异报告，扩展到完整样例集。
5. 在 CI 开启强制门禁后移除旧路径；若出现严重回归，可回滚到旧路径并关闭新门禁开关。
