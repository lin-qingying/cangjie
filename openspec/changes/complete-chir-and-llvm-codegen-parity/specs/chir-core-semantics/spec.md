## ADDED Requirements

### 需求:CHIR 核心语义模型完整化
编译器必须提供可独立消费的 CHIR 核心语义模型，覆盖模块、符号、类型、表达式、语句、控制流与常量语义，禁止以“占位节点”替代真实语义节点进入代码生成阶段。

#### 场景:消费端读取完整 CHIR 模块
- **当** 后端读取一个包含函数、全局变量与控制流的 CHIR 模块
- **那么** 模块内每个符号与节点都必须可解析到明确语义类型，并可被 lowering 阶段直接消费

#### 场景:禁止未建模节点透传
- **当** CHIR 中出现未建模或实验性节点
- **那么** 编译器必须在校验阶段报错并阻止继续 lowering

### 需求:CHIR 一致性校验与结构化诊断
编译器必须在 CHIR 进入 lowering 前执行一致性校验，并通过结构化诊断管线报告错误，禁止以通用异常替代可定位的编译诊断。

#### 场景:类型不一致
- **当** CHIR 节点的输入输出类型不满足定义约束
- **那么** 校验器必须产出带位置信息与错误类别的诊断，并终止代码生成

#### 场景:控制流断裂
- **当** 基本块存在不可达跳转目标或缺失终结指令
- **那么** 校验器必须报告控制流错误并禁止生成 LLVM IR

### 需求:CHIR 访问接口与实现解耦
CHIR 模块对外必须通过接口优先的只读 API 暴露，禁止跨模块直接依赖具体实现细节。

#### 场景:后端通过抽象读取 CHIR
- **当** lowering 组件消费 CHIR 数据
- **那么** lowering 仅依赖公开接口，不依赖具体实现类或可变内部状态
