## 新增需求

### 需求:CFIR_RESOLVE 语义必须对齐官方仓颉编译器
系统必须以 `external/cangjie_compiler/src/Sema` 与 `external/cangjie_compiler/include/cangjie/Sema` 为语义对齐基线，禁止仅按 Kotlin/K2 行为近似实现而忽略仓颉语义差异。

#### 场景:语义规则存在官方映射
- **当** 新增或修改 resolve 语义规则
- **那么** 规则文档与诊断实现必须包含对应官方实现文件/函数映射，能够追溯到具体语义来源

### 需求:extend 与继承相关语义必须完整对齐
系统必须完整实现仓颉 extend 语义与继承约束，包括非法 extended type、非接口继承、重复接口、特化冲突与孤儿规则约束，禁止仅覆盖重复与基础类型检查的子集。

#### 场景:extend 语义全量约束生效
- **当** 代码同时出现 `extend`、泛型特化 `extend`、跨包接口扩展和重复继承接口
- **那么** resolve 必须给出与官方语义一致的接受/拒绝结果和对应诊断

### 需求:BODY_RESOLVE 必须覆盖仓颉核心表达式语义
系统必须在 `BODY_RESOLVE` 阶段完成核心表达式的类型与引用语义解析，包括但不限于调用、控制流、match、spawn、模式相关表达式，禁止将该阶段保留为空推进。

#### 场景:复杂函数体完成语义解析
- **当** 函数体同时包含调用链、条件分支、match 分支与 spawn 表达式
- **那么** 各表达式必须具有可消费的语义结果（类型、目标绑定、错误节点），并可被 CHECKERS 阶段稳定消费

### 需求:诊断输出必须包含稳定语义身份
系统必须为关键语义规则提供稳定诊断标识与可追溯描述，禁止输出不可定位来源的临时字符串诊断。

#### 场景:语义诊断可追溯
- **当** 触发任一对齐规则相关错误
- **那么** 诊断必须包含稳定 factory 名称，并可映射到明确规则身份与语义来源
