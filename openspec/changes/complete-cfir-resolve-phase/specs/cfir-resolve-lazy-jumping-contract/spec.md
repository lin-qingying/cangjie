## 新增需求

### 需求:Jumping Phase 白名单必须固定且可审计
系统必须显式维护 Jumping Phase 白名单，并且白名单变更必须可追溯；禁止通过隐式条件临时放开阶段跳转。

#### 场景:白名单外阶段请求跨声明跳转
- **当** 非白名单阶段发起跨声明 lazy resolve 请求
- **那么** 系统必须拒绝请求并记录受控错误信息

### 需求:Same-phase 重入必须仅限规定阶段
系统必须仅允许 `IMPLICIT_TYPES` 与 `BODY_RESOLVE` 发起 same-phase lazy resolve，禁止其他阶段同阶段重入。

#### 场景:IMPORTS 发起 same-phase 请求
- **当** IMPORTS 阶段请求另一个声明解析到 IMPORTS
- **那么** 系统必须拒绝并保持当前解析上下文可继续执行

### 需求:Jumping 调度必须遵守单调阶段推进
系统必须保证每个声明的 phase 只前进不回退，且 jumping 请求不得绕过前置阶段。

#### 场景:请求跳到更高阶段
- **当** 当前声明处于 TYPES 且尝试请求目标声明直接到 BODY_RESOLVE
- **那么** 系统必须先确保目标声明完成 STATUS 与 EXTENSIONS、IMPLICIT_TYPES 的前置路径

### 需求:Jumping 机制必须具备循环检测与受控退出
系统必须在跨声明依赖图中检测环路，并以受控方式退出，禁止无限递归、栈溢出或死循环。

#### 场景:声明 A/B 互相请求
- **当** 声明 A 在允许阶段请求 B，B 又回请求 A
- **那么** 系统必须通过循环检测中断重入并保留可诊断信息

### 需求:Jumping 执行必须具备幂等保证
系统必须保证同一声明在同一目标阶段的重复请求不会改变语义结果与诊断集合。

#### 场景:重复请求同一目标阶段
- **当** 对同一声明重复发起 lazy resolve 到同一 phase
- **那么** 返回的阶段状态、语义绑定与诊断集合必须一致

### 需求:Jumping 机制必须保证 total/lazy 语义一致
系统必须保证采用 total resolve 与 lazy resolve 最终到同一目标阶段时语义与诊断一致。

#### 场景:两种模式对齐
- **当** 同一文件分别以 total 与 lazy 方式推进到 CHECKERS
- **那么** 最终声明阶段与诊断输出必须一致

### 需求:Jumping 失败路径必须可观测
系统必须为 Jumping 拒绝、循环中断、非法同阶段重入等失败路径输出稳定可测试的事件或诊断信息。

#### 场景:非法请求可观测
- **当** 发生非法 jumping 请求
- **那么** 测试必须能够读取到稳定失败标识并断言具体失败类型
