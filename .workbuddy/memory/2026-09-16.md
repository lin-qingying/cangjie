## 官方编译器语义要点（`external/cangjie_compiler`，只读取证）

**两种形态必须分开实现**

- **形态 A**：`cjc -d` 独立声明编译 → 只出 `.cjo`。
  `CjdCompilerInstance`（`include/cangjie/FrontendTool/CjdCompilerInstance.h:22-63`）裁掉
  DesugarAfterSema / GenericInstantiation / OverflowStrategy / CHIR / CodeGen，只做 `SaveCjo`；`buildTrie=false`。
- **形态 B**：依赖包 `.cjo` 同目录同名 `.cj.d` 作为 sidecar。
  `CompileStrategy::ImportPackages` → `ParseAndMacroExpandCjd`（`src/Frontend/CompileStrategy.cpp:293-332`）：
  Parse + MacroExpand + `MergeCusAnno`，**不做 Sema**，`.cj.d` 的 Package 是**局部对象、不注册进 ImportManager**。

**关键语义（此前容易理解错的）**

1. `parseDeclFile`（`Parse.h:73-86`）是**纯诊断抑制开关**，全部作用点只有 6 个：
   `DiagMissingBody`（ParserDiag.cpp:1216）/ `DiagConstVariableExpectedInitializer`（:1084）/
   `DiagExpectedInitializerForToplevelVar`（:1111）/ `DiagMissingPropertyBody`（Parser.cpp:396）/
   `HAS_BROKEN` 抑制（ParseDecl.cpp:539,582）/ `CheckFuncBody` 整块（ParseDecl.cpp:1550）。
2. **`.cj.d` 的无体函数不标 ABSTRACT**（`isMember && !parseDeclFile`），即存在第 4 种状态
   "无 body + 无 abstract + 语言接受"。**绝不能简单标 abstract**。
3. **但无 `{}` 的类/接口成员属性仍标 ABSTRACT**（`Parser.cpp:371-390`，该分支不看 `parseDeclFile`）。
   函数与属性**不对称**，必须分别实现。
4. sidecar 路径推导 = 把 `.cjo` 路径的 `.cjo` 后缀替换为 `.cj.d`（同目录同名，`ImportManager.cpp:289-295`）。
5. sidecar 匹配键：标识符 + astKind + 泛型形参（数量+名字）+ 泛型约束（类型+上界）
   + 参数（数量+名字+类型）+ extend(被扩展类型+继承列表) + var/prop(类型)。
   **不比较返回类型、不比较修饰符**。
6. 合并只搬 `annotations`，方向恒 `.cj.d → .cjo`，搬完即从源清除；Demo 校验 `FullMoveCheck`。
7. 注解在 APILevel 检查结束时由 `ClearAnnoInfoOfDepPkg`（`CheckAPILevel.cpp:284-304, 708-709`）清除。
8. 未覆盖的注解位置（与官方一致，作为已知限制）：类型参数注解、属性 getter/setter 注解。

**官方实现缺陷（本仓有意不跟随，已在文档标 DIFF-1/2/4）**

- `MergeAnnoFromCjd.cpp:395` 内层循环上界用外层 `genericConstraints.size()` → 潜在越界。
- 匹配用 `unordered_map + find_if` → 顺序不确定。
- `ImportManager.cpp:292` 用 `rfind(".cjo")` 截断整条路径 → 目录名含 `.cjo` 时错误。

## 设计决策摘要（D1-D10）

- D1 独立 FileType（继承 `open class CangJieFileType`）+ **复用 `CangJieLanguage`**，用 `patterns="*.cj.d"`（extensions 表达不了双后缀）。

- D8 `CjSourceKind` 用带默认实现的接口属性引入（避免破坏 `CjSourceFile` 的 4 个实现类）。
- D9 形态 A 的 `.cjo` 产出交给外部 `cjc -d`；本仓 `compiler/frontend` 只提供 declaration 源收集与 CFIR。
- D10 不新增"声明模式"专有诊断（官方也只是抑制旧诊断）。

### 推翻了 v1 的 3 个错误结论（重要，别再用 v1 的说法）

1. **"CLI 参数 DSL 与生成产物有漂移（gen 有 `useFir`）"——错**。
   `useFir` 是 `CommonConfigurationKeys.kt:178-180` 的 `CompilerConfiguration` 扩展属性，与 CLI 参数无关。
   生成物 6 属性 = DSL 4 条 + 生成器合成 2 条（`frontend-arguments-generator/.../Main.kt:116`
   的 `additionalSyntheticArguments = listOf("autoAdvanceLanguageVersion","autoAdvanceApiVersion")`）。**无漂移**。
2. **"不改 `createFile` 会让 `.cj.d` fallthrough 到 `PsiPlainTextFileImpl`"——错**。
   `CangJieParserDefinition.kt:106-115` 的 `when` 首条是 `is CangJieFileType`，而 `CangJieDeclarationFileType`
   **继承**它 ⇒ 会被接住，**永远走不到 else**。真实故障是「静默降级为 `isDeclarationFile=false` 的普通 CjFile」
   ⇒ 编辑器报满屏 `Function body expected`，而高亮/折叠全正常。**验收断言必须写成"无波浪线"，不能写成"不是纯文本"**。
   （`.cjo` 能走 else 是因为 `CangJieBuiltInFileType` 是独立 `FileType` object，不继承 `CangJieFileType`。）
3. **`CjFile.getFileType()` 决策翻转：本次就改**（v1 说"不改，列技术债"）。
   爆炸半径已枚举：psi 内 `getFileType()` 覆写只有 `CjFile.kt:66` 一处；`CangJieFileType.INSTANCE` 的 6 处引用
   **无一读取 `PsiFile.getFileType()`**；`CjFile` 只可能由 `createFile` 两个分支创建 ⇒ 取值域只有
   `CangJieFileType` / `CangJieDeclarationFileType` 两个值 ⇒ 改动安全。不改会留下
   `psiFile.getFileType() ≠ viewProvider.fileType` 的自相矛盾状态。

### 框架缺陷的硬实证（这些是可以直接引用的调研结论）

- **`ParsingContext` 14 个预设，全仓只用到 2 个**：`DEFAULT`（6 次）+ `ANNOTATION_ONLY`（1 次）。
  其余 11 个（`REPORT`/`SILENT`/`IF_WHILE_CONDITION`/`MATCH_EXPRESSION_MODE`/`FUNCTION_LITERAL_*`/
  `MACRO_BACK_TOKEN`/`NO_STRING_INTERPOLATION`/`LEGACY`）**零使用点**。
  ⇒ 这套机制的**实际职责只是"给文件入口选一种解析模式"**，把它当"细粒度局部开关"承接声明模式是语义错配。
  ⇒ 且每个预设都是**全新实例** ⇒ 若声明模式作为其字段，任何局部 `with(其它预设)` 都会**静默丢模式**（今天无调用点，故未发作）。
- **`CangJieParsing` 构造不带文件信息**：`createForTopLevel(builder, languageModuleName)` →
  `CangJieParsing(builder, isTopLevel, isLazy, languageModuleName)`（`CangJieParsing.kt:159-171`）
  ⇒ 解析器**不知道自己在解析哪个文件** ⇒ 模式只能靠调用点选/函数体硬编码。
- **`CjFile` 破坏半径极小**：定义 `psi/.../psi/CjFile.kt:392`，构造/子类点全仓**仅 3 处**
  （`CangJieMacroCallFileType.kt:20`、`CjCodeFragment.kt:53`、`CangJieParserDefinition.kt:110`）
  ⇒ 直接改成持有 `sourceKind` 完全可行，**不需要**为"避免破坏 4 个实现类"而引入 `CjSourceKindCarrier` 过渡抽象。
- **`DeclarationCheckers` 是 `abstract class`（`cfir/checkers/src/.../declaration/DeclarationCheckers.kt:13`）**，
  槽位全按"声明种类"分（basic/callable/function/classLike/property/constructor/extend…），
  注册是**集合粒度** `useCheckers(CommonDeclarationCheckers)`（`CheckersContainers.kt`）
  ⇒ 想按"实现完备性"关一批 checker，粒度对不上 ⇒ 只能下沉到每个 checker 内部 early-return（12 处）。

### 结论：7 处必须破坏性改动（F1-F7）

- **F1**：新增统一 `reportMissingBody()` 上报入口 ⇒ 抑制点 7→1；同时**修正 B 组 5 点的诊断消息**
  （它们报 `function.body.expected` 是**语义误用** —— `func }` 的真实问题是缺标识符）。
  ⚠️ 这是唯一有**外部可见行为变化**（5 处错误文案）的改动，需单独提交/评审。
- **F2/F3**：模式上移为 `CangJieParsing` 的**构造属性** `sourceKind`，不进 `ParsingContext`；
  顺带删除 11 个死预设（可独立提交）。
- **F4**：`CjSourceKind` 为唯一真源，`CjFile` 直接持有它（`isDeclarationFile` 退化为派生属性）。
- **F5**：给 `CfirChecker` 加 `requiresImplementation: Boolean` 默认属性（默认 false=保留），分派处统一过滤
  ⇒ 豁免点 12→1，**新增 checker 默认正确**（作者不需要知道 `.cj.d`）。
- **F6**：`CjdSidecarLocator` 的纯路径部分下沉 `common`，消掉 `project-model` 的内联复制。
- **F7**：PSI / LightTree 两条解析路径的模式判定收敛到一处（F2 的自然结果）。

判据 J1-J5（新增同类实体是否需人工枚举 / 事实是否多源 / 局部是否覆盖全局 / 新实现者是否需知道特性存在 / 同源路径是否共享机制）

### 实现时发现的事实（设计稿之外）

1. **`reportMissingBody` 定稿不是"单一消息"，而是"单一抑制点 + 按 owner 传消息"**。
   设计稿原写 `reportMissingBody(owner: String)` 且忽略 owner、固定上报 `function.body.expected`。
   但 P4 的属性诊断（`unimplemented.abstract.property` + `missing prop body`）表达的是
   "非抽象类里出现无体属性"，塌缩成"Function body expected"会**丢失真实信息**。
   ⇒ 改为 `reportMissingBody(report: () -> Unit)` + 一个默认文案重载。
   **抑制判定仍是唯一一处**（框架正确性的落点），消息文本本来就跟 owner 相关。
2. **`parseInitFunctionBody` 的 `at(COLON)` 恢复路径必须"早退"，不能只抑制 error**：
   ```kotlin
   val error = mark(); while (!at(LBRACE)) advance(); error.error(...)
   ```
   `.cj.d` 里没有 `{` 可恢复 ⇒ 循环会 advance 到 EOF **吞掉文件其余内容**，
   且 `mark()` 无 done/error 破坏标记平衡。⇒ 声明模式下整块跳过并消费返回类型。
   **推论：凡"抑制点"同时伴随恢复动作（mark+advance 循环），必须按"早退"处理。**
3. **`parseMacro` 的触发输入不能是裸 `macro }`**：`macro package <name>` 是**合法文件前导**，
   `parsePackageDirective`（`CangJieParsing.kt:697-703`）会把**处于文件首位**的 `macro` 当宏包声明头吃掉
   （报 `Expecting 'package' keyword`），到不了 `parseMacro`。用例须用 `@Foo\nmacro }`。
4. **`:3595`（`parsePrimaryInitFunc` 的 `at(RBRACE)` 守卫）实测不可达**：唯一调用方要求
   `at(IDENTIFIER) && lookAhead(1) == LPAR`，`advance()` 后必为 `LPAR`。保留为防御分支，不写用例。
   （设计稿原写的触发文本 `class C }` 也是错的。）
5. **`parseMacro` 的分派包在 `with(parseContext.copy(...))` 里**（`CangJieParsing.kt:2568-2571`）——
   这是"模式不能放进 `ParsingContext`"的**现场证据**：`copy(...)` 整体替换上下文，
   存进去会被静默清掉，无任何信号。4.2.3 的论证由推理升级为实测。
6. **宏调用文件入口是独立的 `CangJieMacroCallParserDefinition`**：其 `createFile` 返回
   `CjMacroCallFile`（`sourceKind` 覆写 MACRO_CALL）⇒ C-1 的"收敛到 `sourceKind`"是**等价替换**。
   非 `CjFile` 的兜底改用 `CjSourceKind.fromFileName(psiFile.name)`（保留原"按名字识别"能力，不丢）。
7. **诊断点计数**：`function.body.expected` 从 7 → **1**（只在 `reportMissingBody` 默认重载）；
   `expecting.symbol "{"` 从 10 → **6**（排除清单 5 + 恢复路径 1）。这个数字是回归防线。
8. **文案变更范围是 9 处**（B 组 5 + A 组 4：getter/setter/parseFunction/main），
