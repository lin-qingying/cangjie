## ConstraintCheck `option_with_element_01`（唯一未修复项，已定位到「约束注册时机 vs 变量固定时机」）

- 官方 cjc 1.0.5 实测：`f(1, Some(1))` 等四个调用**零诊断**，`T` 推成 `Option<Int64>`
  （`let a: Option<Int64> = g(1, Some(1))` 通过、`let a: Int64 = ...` 报推断失败）。
  即下界 `Int64` 与 `Option<Int64>` 参与同一个 Join。
- CFIR 实测（插桩）：
  - 两个实参分别添加 `LOWER Int64 <: T`、`LOWER Option<α> <: T`（`α` = `Some`/`Option` owner 变量）。
  - 但 `ResultTypeResolver.findSubType` 在固定该变量时只看到 `lowers=[A]`/`[Int64]`，
    即 `Option<...> <: T` **尚未进入该变量下界集合**；随后 `Option<Int64> <: T=Int64`
    记为 `ConstraintError`，经 `hasGenericInferenceConstraintMismatch` 归一成 `UNABLE_TO_INFER_GENERIC_FUNC`。
  - `processVariableWhenNotEnoughInformation` 全程未触发（`notEnough=false`）→ 不在"信息不足"分支。
- 结论：**不是 fixture 期望错误**，也不是诊断选择问题；需保证固定候选变量前同一调用的
  第二实参约束已注册（或枚举构造器实参推断先于外层变量固定完成）。**未落地推测性改动。**

## 教训：范围/期望改动必须由 cjc 或 C++ 源码背书

本轮走过一次弯路：`record_mut_invalid_11` / `record_extend_mut_invalid_7` 期望
`<!USE_MUTABLE_FUNC_ALONE!>obj.foo<!>`（整段限定访问），我按 Diagnostic Range Policy
"比单个标识符更复杂的构造以 Kotlin 对位为准"把生产者从 `calleeReference.source` 放宽到
`expression.source`，结果**为了让 2 个失败用例通过，去重写了 3 个原本通过的用例**
（`record_mut_invalid_17/_18`、`unsafe_func_can_only_be_called`）。已全部回滚。

- 正确读法：Policy 是"把 cjc 的首字符锚点展开成完整 token"。cjc 对
  `sema_use_mutable_func_alone` 锚在成员名 `foo`（实测 `[L11:C9→C12)`），展开后就是 `foo`，
  不是 `obj.foo`。"更复杂的构造"那条只适用于锚点本身不是单个 token 的场景（如 `extend R <: I {`）。
- 语料本身 3:2 偏窄（17/18/unsafe 窄且原本通过），应当修正 2 个离群 fixture，而不是改实现。
- **硬规则：不得为了让失败用例变绿而改写原本通过的期望；语料内部自相矛盾时先停下问用户。**
